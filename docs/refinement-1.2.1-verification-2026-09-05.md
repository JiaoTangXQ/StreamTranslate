# 1.2.1 本机增强验收

状态：**1.2.1 build 9 已签名安装到 `/Applications/StreamTranslate.app`，可直接使用。** 采用 Apple 快速路径 + Qwen 0.6B + Hy-MT 1.8B。最终 build 8 推理链路通过中英文正式系统音频检查；build 9 只修复设置窗口被字幕遮挡，已编译并目视核验。录制停止、Diagnostics 关闭、恢复 English + System Audio，两个增强开关开启，模型进程在停止后释放。7B/4B 未替换默认模型。不能将本页解读为数学意义上的速度/准确率极限。

下面保留中间版本的实测与失败记录：build 4–7 曾有不同断句回归，最终采用 build 8 的停顿式策略；最终交付与限制见末节。不能将中间版本安装成功理解为质量检查通过。

## 选型

目标机器为 Apple M4、16GB 统一内存、macOS 26.4。本轮已验证的结构为：

- Apple Speech 流式识别和 Apple Translation 快速显示。
- Qwen3-ASR 0.6B Q8 原生 Metal，在句尾复核原文；不替代流式识别，也不重放音频给 Apple。
- 独立原生 Metal 翻译模型精修中英双向终稿。快速译文不等待它；缺模型、超时、内存压力时保留系统路径。1.8B 已完成 320 秒长测，7B 因长测内存压力被排除为默认常驻选择。

这些模型已在本机实际运行，不需要 Windows、CUDA 或英伟达显卡。App 的原生推理不依赖研究用 Python 环境。权重在 PortableSSD；Qwen 约 1.35GB，默认 HY 为 1.8B Q4_K_M。7B 的约 4.62GB 仅是对照权重磁盘文件大小，不是统一内存占用承诺。

1.8B 翻译权重是本轮选定的默认精修模型。7B 在中文归因、最终一致性、技术句因果关系等对照上有收益，但并非每句都更好。Qwen 1.7B 未在本组音频展示足以抵消资源/延迟开销的收益，因此不作为默认 ASR 复核。Nemotron 保留为可选英文流式后端；新组对照中首字较早不等于字幕翻译更早。

## 确认的链路修正

- 草稿保留词边界和适量尾部上下文；有足够内容时最多等待 600ms 进入调度，不再单靠五词/十字门槛。该时间不包含识别和翻译计算。
- 冲突假设不拼接到旧冻结前缀；两次新的音频证据允许纠正冻结错误。抑制 `We ruled`、`我们已经` 等容易产生错误早译的碎片。
- 中文只在真实停顿和实质识别文本满足条件时请求确认，不按时长强切、不重启识别器；最终音频范围可修剪静音，仍退役对应草稿。连续不换气的长句可能延后精修，草稿继续流式显示。
- 源复核使用纯句段与上下文音频两个视角；普通词可由同段前一个原始 Apple 假设佐证。两次 Qwen 解码不是独立模型投票。
- 纯句段不再进行半全局裁剪；仅将原文已出现的等值整数百分数统一书写，避免 `ninety-five percent` 对齐 `95%` 时丢失句尾。已知数量、否定信息和明显截尾受保护。复核不新增跨句引号作用域。
- 精修上下文限于本场前两句、最多 600 字符，只推导受限术语或明确同主语 `used to … / no longer do` 省略的自足翻译输入。原始背景不再发送给翻译模型，原文 ASR 不改写。
- 数值变化对比使用额外提示，区分“变化了多少”和“变化到多少”。有明确百分比原文、且没有百分点时，仅纠正输出误写的百分点单位，不修改数值；原文明示百分点时保留它。
- 数字/分数不一致、完全丢失显式否定、提示标签泄漏等结果不能覆盖快速译文。这不是完整语义验证器；未识别的表达仍可能错译，部分合法改写可能保留系统译文。
- 每个增强阶段最多一项执行、两项等待；迟到结果不能覆盖更新后的原文或清空后的历史。内存 warning/critical 释放增强进程，不中断基础字幕，本场不反复重载。

## 长测发现与后续

320.504 秒混合英文连续回放完成于 320.642 秒，111 个原始最终结果对应 111 条字幕，四类关键语句各出现预期的 10 次，日志没有采集/管线错误。但约 115 秒时出现系统 memory warning，增强模型被释放，后续由系统路径完成。末尾 0.115 秒滞后因此是**降级后**的值，不是 7B 的持续性能。保护机制有效，也证明短测不足以支持 7B 默认常驻。这不是内存占用仅看文件大小或父进程 RSS 就能发现的限制。

新增受限软件术语对照：前文有 memory leak/model weights/key-value cache 等明确线索，且没有租金、租客、房东等语境时，只为 cash eviction/key-value cash 等匹配片段提供术语映射，不把完整背景交给模型，也不改写源 ASR。3 条技术对照改善、5 条财务/不相关/混合语境控制不变。新增用例后共 220 个核心用例通过。

1.8B 的 320.504 秒持续压力测试已完成，未观察到本场内存降级。最低系统盘余量 2,965,561,344 bytes，系统 swap 6131.06→6107.06MB。期间有外置盘模型下载，因此用于验证持续运行/资源回退，不将其中数字作为干净的单模型速度排名。测试暴露的背景复制已修正：随后 26.828 秒的三遍归因语音均将 `I no longer do` 译为“我不再认为这次更新是安全的”，未复制前文，末尾可见修正滞后 0.432 秒。证据：`ellipsis-fixed-replay.jsonl`。

另在核实 [Google TranslateGemma 4B](https://huggingface.co/google/translategemma-4b-it)：[Google 发布说明](https://blog.google/innovation-and-ai/technology/developers-tools/translategemma/) 将 4B 定位于边缘部署，但本机可用性、中文质量及持续资源占用仍需实测。下载的是公开的 [bullerwins 社区 GGUF](https://huggingface.co/bullerwins/translategemma-4b-it-GGUF)，不是 Google 官方量化，固定 commit `7c938465a870d8624bcfa98a8e4a3510053c19a8` / SHA256 `7f7357c14abd9da4eb200b38b05da502cd6e10d7e1d403fbc9f78c19f3209b72`，2,489,909,312 bytes。未代用户接受 gated 许可页面或使用账号凭证；下载完成也不等于验证通过。

## TranslateGemma 4B 对照结论

公开社区 GGUF 已下载并核对上述 SHA256，在本机通过 llama.cpp b10809 Metal 实际生成。服务启动的聊天能力探测不支持其结构化 content，因此对照直接渲染模型内嵌 Jinja 模板，以显式语言代码和单个源文本生成 token 后调用 `/completion`；未把 Hy-MT 提示当作它的官方模板。贪心解码，48 条同题文本中位处理约 0.804 秒、最大 1.49 秒（含本地 tokenize 请求），慢于此前 1.8B 中位 0.309 秒；不同模型采用各自模板，不是隔离架构的控制实验。

有收益：中文人物归因、部分数值关系。明显退化：eventual consistency 译作普通“最终保持一致”；feature flag 中文转英文扩成“all functions”；含 ASR 标点歧义的缓存句仍译出错误因果关系。12 条数值对照中，`The budget was reduced by half, not to half a million dollars.` 误译成“只减少到50万美元，而不是500万美元”，输出新增金额；另一条增加量/最终值仍混淆。因此不默认替代已有轻量增强，也不增加第二个常驻翻译模型。结果保留在 `translategemma-4b-{expanded,numeric}.jsonl`，模型留在外置盘用于复核。

## 中文实机边界回归与 build 5

build 4 的英文实际 ScreenCaptureKit 会话采集 92.7 秒（包含开始/结束静音），22 个原始最终结果和 22 次精修，译文处理中位 222ms、最大 371ms，无采集序列缺口/超过 50ms 的源音频间隙或管线错误。截图确认长历史跟随和同条目更新。App 自身峰值 footprint 58MiB **不包含外部模型进程/GPU 内存**。

中文四段紧接播放发现：录制开始约 6 秒后才发声，14 秒强制确认却从录制起点计时，把“模型权重没有变大”割成“模型权重没有｜变大”。此缺陷在无前置静音的单条测试里未出现。build 5 按当前发声起点计时，且强制确认不能落在“没有/尚未/只要”等未完成尾部；暂停处确认仍覆盖完整已接收音频，不重启识别器。

另外，复核器在原文连续“问题出在”中间插入逗号，让小模型错译因果关系。8 条额外提示对照未修复主例，因此不启用该提示。仅保护源文本已有的短语边界：把复核新增的内部逗号移到短语前，不改任何词；原文已含该内部逗号或混合出现时不作此修复。首部短语不新增前导逗号。

使用失败会话的 **同一份 53.94 秒系统录音** 重放，build 5 的第一段已完整保留“模型权重没有变大”，英文明确为 “We have ruled out memory leaks; the problem lies in the cache eviction strategy.”，不再把已排除项说成真实原因。该次重放其余条件、百分数、归因段保持完整，但后续实际播放仍发现时间强切的问题，故继续修正。录音含首尾静音，不能把相对整段文件的负末尾滞后当成更快的性能指标。证据：`captured-chinese-boundary-fixed.jsonl`、`captured-chinese-final.jsonl` 及对应资源记录。

## 最终交付验收

最终不再以聚合 result.range 的末尾作为时间强切位置。只有真实 450ms 停顿、至少 4 个语义单元、当前发声跨度至少 4 秒且没有未闭合的“只有…才…”/“只要…就…”时才请求确认。数字尾部属于草稿保护，不阻止在真实停顿处解码完成百分数；否则 `98` 的部分结果等待 `%` 时会错过停顿、并入下句。没有实质识别文字的噪声/孤立单字不触发此请求。系统自身最终结果和停止收尾照常生效。

build 8 正式 App 的中文四段连续播放形成 **3 条完整最终字幕**（条件与数字段合并，未丢字/误切）。否定、条件、95%→98%、变化量/最终值、人物归因均正确保留；一次 HY 精修未通过完整性校验，保留了 Qwen 修正原文后已经正确的 Apple 译文，不能称作“所有模型请求都成功”。77.56 秒采集含测试前后静音，3878 个音频块，无序列缺口或超过 50ms 的源音频间隙。3 次源复核、2 次被接受的精修；精修 647/673ms。App 自身峰值 footprint 55.8MiB，不包括增强模型/GPU。

切换回英文后，归因/省略测试形成 4 条最终字幕，4 次精修全部完成，`I no longer do` 正确译为“我不再认为这次更新是安全的”。35.88 秒采集同样包含等待静音，无采集缺口或管线错误；精修 158–257ms（p50 239ms）。这不是包含冷启动的首译或端到端延迟。两次停止都完成最终收尾，随后无遗留 QwenHelper / llama-server / 回放 / afplay 进程。
